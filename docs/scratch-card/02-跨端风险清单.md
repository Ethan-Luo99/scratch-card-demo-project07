## R1 旧 CanvasContext 在微信小程序已停止维护

- **风险描述**：`uni.createCanvasContext` 在微信端对应的旧版 Canvas 2D 接口（CanvasContext）官方已标注「停止维护」，不再修复缺陷；其渲染走非同层的原生组件，且部分新能力（如标准 `getImageData`、`requestAnimationFrame`）不可用或行为弱化。若主路径选旧 API，未来基础库升级存在失效风险。
- **受影响平台**：微信小程序（主）；App-vue 旧内核仅作回退影响。
- **触发条件**：使用 `uni.createCanvasContext(canvasId, this)` 并依赖 `ctx.draw()` 模式；或在高版本基础库上期望其与新版一致的合成/像素行为。
- **验证方法**：对照 D1 页首「注意」原文；在最新版微信与基础库 2.x 低版本（如 2.10.x）各跑一段 `fillRect + draw(false, cb) + canvasGetImageData` 回调，记录是否正常；真机预览时用「调试 → 性能面板」观察 draw 调用帧率。
- **缓解措施**：主路径强制使用 `<canvas type="2d">` + SelectorQuery node（§3 选型 B，依据 D1/D2/D7）；旧 API 仅在 App 旧内核探测不到 node 时作为回退，且回退分支的像素判定不依赖其同步读数据能力；在 `Failed` 态收集 SDKVersion 以便收敛兼容范围。

## R2 H5 canvas 是真 DOM，小程序/App 是组件，节点获取模型不同

- **风险描述**：H5 端 `<canvas>` 编译为标准 DOM 元素，可直接 `document.querySelector`、`el.getContext("2d")`、用 `getBoundingClientRect()`；小程序/App 端 canvas 是注册组件，必须在组件/页面 ready 后通过 `uni.createSelectorQuery().in(实例).select(id).fields({node:true,size:true,rect:true})` 异步获取节点，且 HBuilderX/基础库版本不同时 node 字段可能为 null。
- **受影响平台**：三端（差异点在 MP/App）。
- **触发条件**：在 `setup` 同步阶段取节点；未传 `.in(this)` 导致组件内选择器返回 null；H5 分支误用 SelectorQuery 的 node（H5 node 字段行为与小程序不一致）。
- **验证方法**：分别在 H5、微信开发者工具 + 真机、App 标准基座真机打印 exec 回调结果；在「组件内」与「页面内」两种放置位置各测一次（验证 `.in(instance)`）；弱网/慢渲染下延迟 1s 再 ready 复测。
- **缓解措施**：适配层 `mount()` 封装三端获取逻辑（H5 走 DOM、MP/App 走 SelectorQuery），统一返回 `CanvasSurface`；ready 时机统一在页面 `onReady`（uni-app 页面生命周期）之后；node 为 null 时区分「旧内核（回退 R14）」与「真失败（Failed 态）」；依据 D5/D7。

## R3 旧原生 canvas 的层级问题与 cover-view 嵌套限制

- **风险描述**：旧版 canvas（以及回退分支）是原生组件，普通 view 无法覆盖，z-index 无效；唯一覆盖手段 `cover-view` 仅支持嵌套 `cover-view`、`cover-image`、`button`，不支持绝大多数样式（渐变、阴影、部分 flex 表现、复杂子组件），无法承担奖品图文层。
- **受影响平台**：微信小程序（旧接口时）、App-vue（旧 webview 内核）；H5 无此问题。
- **触发条件**：奖品文案用普通 view 放在 canvas 之上；或用 cover-view 放富文本奖品/按钮；或页面内有弹窗、吸底按钮与旧 canvas 区域重叠（弹窗被 canvas 穿透盖压）。
- **验证方法**：开发者工具「真机调试」模式（工具内同层模拟不可信，必须真机）观察文案是否被 canvas 盖住；cover-view 内放 image+多行文本+次级按钮看样式丢失；上下弹出 popup 经过 canvas 区域验证遮挡。
- **缓解措施**：选型新版 Canvas 2D 同层渲染（D3 同层组件清单含 canvas 2D），奖品层放 canvas **下方**普通 view（§7），彻底不用 cover-view；App 旧内核回退在揭晓时直接隐藏 canvas 再露 view；任何弹窗在 Scratching 态禁用或提高挂载时机（Revealed 后）。依据 D3/D4。

## R4 transformPx:false 导致 px 不转换的单位风险

- **风险描述**：本项目 `manifest.json` 已配置 `"transformPx": false`，此时模板与样式中的 `px` 在小程序端不会被编译为 rpx（按真实物理逻辑 px 处理），若按 uni-app 默认模板习惯写 px 尺寸，会在不同宽度机型上错位（750 设计稿的 px 不会自适应）；而 JS 里又不能自行按 750 换算。
- **受影响平台**：微信小程序、App（编译期单位转换差异）；H5 表现也与预期设计稿不一致。
- **触发条件**：canvas/卡片样式写 `width:375px` 等；JS 内手写 `px = rpx * screenWidth/750`；第三方/既有组件携带 px。
- **验证方法**：在屏宽 320/360/390/414 及 iPad 分屏宽度下截图比对卡片是否恒占屏宽；全局搜索样式中的 px 单位；对比 transformPx 开关编译产物中 wxss 的单位差异。
- **缓解措施**：卡片相关尺寸**一律 rpx**（rpx 不受 transformPx 影响，D10）；JS 内不做单位换算，统一 SelectorQuery 实测 `size`（§5.1）；仅边框/细分割线允许 1px；CR 检查禁止新增 px 布局尺寸。依据 D10/D11。

## R5 DPR 与物理像素不对齐导致模糊 / 坐标偏移

- **风险描述**：canvas 样式尺寸（CSS px）与节点 `width/height`（物理像素）未按 `pixelRatio` 对齐时，涂层模糊、笔刷边缘虚；`ctx.scale` 重复设置或 scale 后又乘 dpr 会造成笔迹与触点偏移；iOS 部分 WebView pixelRatio 为 3，安卓个别机型返回异常取整值。
- **受影响平台**：三端（App/MP 真机最明显）。
- **触发条件**：忘记给 canvas node 赋 width/height；onShow 后尺寸变化未重设；自行缓存 dpr 跨设备使用（如开发者工具切换机型）。
- **验证方法**：在 DPR 2/3 机型（iPhone 12 系 3x、安卓 1080p 3x、低端安卓 2x）上放大截图检查笔刷边缘；点击固定网格点量测触点与擦除圆心偏差（应 ≤ 1 物理像素）；切换微信开发者工具机型后重进页面复测。
- **缓解措施**：§5.2 统一三步：实测 cssWidth/Height → node.width=round(css*dpr)（dpr 钳制 ≤3）→ 只 scale 一次；onShow/onResize 后重走整套初始化；用 `uni.getSystemInfoSync().pixelRatio` 实时取不缓存。依据 D12。

## R6 触摸坐标换算在滚动/层级/transform 下偏差

- **风险描述**：H5 的 `pageX/pageY` 含页面滚动而小程序 touch 的 `clientX/clientY` 为相对布局视口；若混用 `offsetLeft`、`scrollTop` 会在不同端产生整段滚动距离的偏差；祖先节点使用 CSS `transform` 时 H5 的 rect 已含变换而小程序原生布局不受 transform 影响，坐标系不一致。
- **受影响平台**：三端。
- **触发条件**：卡片在可滚动页面中部；弹层动画给祖先加 transform；使用 `position:fixed` 导航叠加；小程序全屏/沉浸式下导航高度差异。
- **验证方法**：页面顶部撑出 600px 占位使卡片位于折叠下方，滚动到中段后四角点测；H5 分别在桌面鼠标（mousedown/move）与移动模拟 touch 下点测；给祖先临时加 `transform:translateX(10px)` 观察两端偏差。
- **缓解措施**：统一 `x=clientX-rect.left`、`y=clientY-rect.top`，rect 来自 SelectorQuery 的视口坐标，滚动天然抵消（§5.3）；touchstart 缓存 rect、onShow/onResize 失效重查；**约定卡片祖先不使用 transform 位移**（动画只做 opacity 或作用于卡片内部元素）；点坐标 clamp 到画布范围。依据 D5。

## R7 touchmove 高频回读像素导致卡顿/掉帧

- **风险描述**：在 touchmove 内对全尺寸 canvas 同步 `getImageData` 会触发 GPU→CPU 回读与流水线冲刷，中低端安卓单次 5~15ms，叠加擦除绘制后持续掉帧、触摸延迟；部分安卓 touchmove 频率高于显示帧率，回读纯属浪费。
- **受影响平台**：三端（微信小程序/App 中低端安卓最严重）。
- **验证方法**：开发者工具「Performance」/真机 `setPerformance` 面板录制 5s 快速刮动，统计长任务与帧率；对比「move 内读像素」与「rAF 120ms 降采样」两版帧率；在低端安卓（Android 9/10、4GB 内存）真机复测。
- **缓解措施**：§9：move 内只擦除不读像素；rAF（或 canvas.requestAnimationFrame）调度、≥120ms 间隔、drawImage 缩放到 25×14 离屏画布后一次读取 350 点；达标即停循环。依据 D2（Canvas 2D 接口性能模型）。

## R8 抗锯齿/半透明像素造成面积误判

- **风险描述**：round 线帽边缘 alpha 渐变、涂层贴图自带半透明像素、不同 GPU 合成差异，会让「alpha<255 即刮开」的判定虚高，轻划几下就误触发全揭开；反过来阈值过严则刮到 60% 还不揭晓。
- **受影响平台**：三端。
- **触发条件**：单像素点采样、贴图含透明通道、笔刷边缘落在采样点上、阈值临界快速来回涂抹。
- **验证方法**：用脚本化手势（automator 或真机录制回放）分别刮 10%/30%/45%/50%/55%/80% 面积，比对算法 ratio 与离线用完整 `getImageData` 以 alpha≤24 计算的基准值，误差要求 ≤ 5%（见 03 文档）；细划痕（只划一条对角线）后断言不达标。
- **缓解措施**：§6.4：双阈值（24/120）+ 可疑格 0.5 折算 + 揭晓要求净格 ≥ threshold-0.05；区域平均采样；cell 状态单调不可逆；涂层先垫不透明底色；四边坐标 clamp。

## R9 快速甩动断线、多点触控与触摸序列中断

- **风险描述**：touchmove 两点间距大时只画圆点会出现「虚线」；多指同时落下时 `touches[0]` 可能跳指（identifier 切换）造成跨区域连线；来电/系统权限弹窗/onHide 会造成只有 start 没有 end，回前台后首尾两点连成一条贯穿擦除线。
- **受影响平台**：三端（iOS 来电中断、安卓多点跳指更常见）。
- **触发条件**：快速甩动；双指/手掌误触；刮卡中切后台、来电、下拉通知中心。
- **验证方法**：脚本化对角线快速滑动（全程 < 300ms）检查视觉连续性与 ratio；双指交替划动检查无异常连线；刮卡中按 Home/切微信聊天再回来（onHide/onShow）检查画布状态；iOS 真机模拟来电。
- **缓解措施**：按 0.6r 步长线性插值补点（§6.3）；记录首指 `identifier`，move 中只采 `touches` 里匹配该 identifier 的点，不匹配忽略（多指不切换追踪目标）；onHide 与 1s 时间戳 gap 双重结束笔画，回前台按 §8.3 重置（或用 canvasToTempFilePath 保留，首版选重置）。

## R10 涂层贴图加载：域名白名单与异步解码卡顿

- **风险描述**：小程序 `drawImage` 网络图片受 downloadFile 合法域名限制，未配置域名时真机不显示（开发者工具勾选「不校验域名」会掩盖问题）；图片未解码完成就绘制导致首笔空白/卡顿；H5 与 App 的 image 对象创建 API 不同（H5 `new Image()`，MP 2D 用 `canvas.createImage()`）。
- **受影响平台**：微信小程序（域名）；三端（解码）。
- **触发条件**：使用 `coverImage` 网络图；首帧立即绘制；弱网下进入页面即刮。
- **验证方法**：开发者工具关闭「不校验合法域名」后真机预览；弱网（限速 2G）进页面立即刮，观察首笔；贴图不存在/404 时检查降级。
- **缓解措施**：Loading 阶段 `uni.getImageInfo` 预取本地临时路径（内部走 downloadFile，需在小程序后台配置 downloadFile 域名，D14/D13）；适配层内部分别用 `canvas.createImage()` / `new Image()` 并 await onload；失败或未配置时降级纯色涂层；prize 未就绪禁止刮动。

## R11 同层渲染的版本覆盖与「开发者工具可信、真机不可信」

- **风险描述**：canvas 2D 的同层渲染依赖一定基础库版本（旧版微信或被用户长期未更新的客户端可能不支持/走降级渲染），微信开发者工具的渲染表现与真机不一致，工具里层级正常不代表真机正常；App 端则受云打包/自定义基座的 webview 内核版本影响（已知碎片化问题，DCloud 问答区长期存在「canvas type=2d App 端 node 为 null」类反馈）。
- **受影响平台**：微信小程序低基础库、App-vue 各厂商内核。
- **触发条件**：低版本微信、X5/系统 webview 过旧、HBuilderX 版本与运行版本不匹配、使用标准基座而非自定义基座调试。
- **验证方法**：真机覆盖矩阵（见 03 文档）：微信最低支持基础库版本 1 台 + 当前版本 2 台（iOS/安卓各一）；App 用与发版一致的自定义基座在 Android 8/10/13、iOS 15/17 真机验证 node 是否可取；全程真机调试而非工具截图验收。
- **缓解措施**：mount 时探测 node：取不到不报错崩溃，进入 R14 回退或 Failed 态；上报 platform/SDKVersion/内核；管理后台配置小程序最低基础库版本；App 侧在文档中声明最低 webview/系统版本。

## R12 onHide/onShow、结算上报与并发竞态

- **风险描述**：刮卡中切后台 rAF 仍在运行（小程序后台无调用时机但回到前台会积压）；阈值揭晓与用户继续滑动并发产生重复 complete；结算上报失败无补偿导致「刮中但服务端无记录」；Loading 未完成时用户已触摸。
- **受影响平台**：三端。
- **触发条件**：刮卡中切后台/锁屏；阈值瞬间连滑；弱网点「领取」；慢网进入页面立刻触摸。
- **验证方法**：刮到 49% 切后台再回前台继续刮到达标，检查只触发一次 complete；监听网络面板让结算接口 500，重进页面验证补报；弱网下疯狂触摸检查无越界擦除与提前揭晓。
- **缓解措施**：状态机单线程迁移（§8），Revealing 立即解绑事件与停 rAF；complete 在 Revealed 只 emit 一次（状态守卫）；结算失败写 `uni.setStorage` 队列，`uni.onNetworkStatusChange`/onShow 补报；Loading/Failed/disabled 时 touch 处理直接 return。

## R13（补充）rAF 来源与 setInterval 替代的差异

- **风险描述**：H5 用全局 `requestAnimationFrame`；小程序 Canvas 2D 的 rAF 挂在 CanvasNode 上（`canvas.requestAnimationFrame`），页面不可见时行为与 H5 不完全一致；旧 API/旧内核无 rAF，需 setTimeout 兜底。若三端统一用 `window.requestAnimationFrame`，小程序无 window 对象会直接抛错。
- **受影响平台**：微信小程序、App 旧内核。
- **触发条件**：在适配层之外直接调用 window.requestAnimationFrame/cancelAnimationFrame。
- **验证方法**：微信真机刮动中观察采样节流是否生效（埋点打印 check 时间戳）；切后台后回前台检查无积压回调风暴；App 旧内核基座验证 setTimeout 分支。
- **缓解措施**：rAF 由 `CanvasSurface` 内部暴露统一 `scheduleFrame(cb)`：MP 2D 用 node.requestAnimationFrame，H5 用 window.rAF，回退用 setTimeout(16)；onHide 显式 cancel。依据 D2。

## R14（补充）App-vue 旧内核回退路径的可用性

- **风险描述**：旧 App webview 内核无 Canvas 2D node，只能 `uni.createCanvasContext`；旧 API 读像素依赖 `uni.canvasGetImageData`（回调式、坐标按 canvas 逻辑尺寸、返回 data 受内核实现影响），且 draw 是批量异步指令（`ctx.draw(reserve, callback)`），在 draw 回调完成前读像素会读到旧画面。
- **受影响平台**：App-vue（旧内核/旧基座）。
- **触发条件**：未升级基座、低版本 Android WebView。
- **验证方法**：旧版自定义基座真机：快速刮动后检查 draw 回调时序；连续擦除（reserve=true）+ canvasGetImageData 采样，比对 ratio 趋势是否单调；揭晓时隐藏 canvas 检查下方 view 是否正常出现。
- **缓解措施**：回退实现中所有读取在 `draw(true, cb)` 的 cb 内发起；面积判定改走「中心点采样（每格中心单像素）+ 轨迹网格双保险」，读像素失败时以轨迹覆盖格估算并上浮阈值 5%；产品声明旧内核为「可刮、揭晓准确、刮动中无下层透视」的降级体验。依据 D8。

## R15（补充）页面手势冲突：滚动、点击态、下拉刷新

- **风险描述**：卡片位于可滚动页面时 touchmove 会带动页面滚动（小程序需 catchtouchmove 才真正阻止，H5 需要 preventDefault）；H5 鼠标拖拽会选中文本/拖出图片；卡片点击态高亮与长按菜单干扰。
- **受影响平台**：H5（文本选择/鼠标）、小程序（滚动冒泡）、App（橡皮筋回弹）。
- **触发条件**：卡片高度小于页面、内容可滚动；H5 桌面端鼠标操作；iOS 边缘手势。
- **验证方法**：卡片置于长页面中快速横向刮动检查页面是否滚动；H5 桌面鼠标拖拽检查选区；iOS 上沿卡片边缘刮检查是否触发返回手势。
- **缓解措施**：canvas 上 `@touchmove.stop.prevent`（小程序编译为 catch 行为，H5 preventDefault）；卡片容器 `user-select:none`（H5）与 `-webkit-touch-callout:none`；卡片宽度不延伸到屏幕左右边缘（保留 16rpx 安全距离给系统手势）；本页关闭 `enablePullDownRefresh`。
